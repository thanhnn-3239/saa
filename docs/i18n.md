# Internationalization (i18n) — SAA Kudos

**Library:** next-intl 4.13 · **Strategy:** cookie-based, no URL routing · **Locales:** `vi` (default), `en`

---

## How it works

Locale is stored in the `NEXT_LOCALE` cookie (1-year expiry, `sameSite: lax`). On every request, `i18n/request.ts` reads the cookie, resolves it to a supported locale via `resolveLocale()`, and loads `messages/{locale}.json`. There is no locale prefix in URLs — `/login` stays `/login` in all languages.

Key files:

| File | Role |
|------|------|
| `lib/i18n/config.ts` | `LOCALES`, `DEFAULT_LOCALE`, `LOCALE_COOKIE`, `resolveLocale()` |
| `i18n/request.ts` | `getRequestConfig` — reads cookie, returns locale + messages |
| `lib/i18n/locale-actions.ts` | `setLocale(locale)` server action — writes the cookie |
| `messages/vi.json` | Vietnamese strings (namespaced) |
| `messages/en.json` | English strings (namespaced) |
| `next.config.ts` | Wraps config with `createNextIntlPlugin()` |
| `app/layout.tsx` | `<html lang={locale}>` + `<NextIntlClientProvider messages={messages}>` |

No `middleware.ts` changes — locale resolution happens inside `getRequestConfig`, not at the edge.

## Using translations

**Server Components:**

```ts
import { getTranslations } from "next-intl/server";

const t = await getTranslations("Login");
return <h1>{t("welcomeLine1")}</h1>;
```

**Client Components:**

```ts
"use client";
import { useTranslations } from "next-intl";

const t = useTranslations("Login");
return <button>{t("loginButton")}</button>;
```

## Switching language

Call `setLocale(locale)` then refresh the router so Server Components re-render:

```ts
"use client";
import { useRouter } from "next/navigation";
import { setLocale } from "@/lib/i18n/locale-actions";
import type { Locale } from "@/lib/i18n/config";

async function handleSwitch(locale: Locale) {
  await setLocale(locale);
  router.refresh();
}
```

The UI shows uppercase labels (`VN` / `EN`); the cookie stores lowercase (`vi` / `en`).

## Adding translations to a new screen

1. Add keys under a new namespace in **both** `messages/vi.json` and `messages/en.json`.
2. Use the same namespace string in `getTranslations("YourNs")` / `useTranslations("YourNs")`.
3. A test enforces key parity between the two files — the build will fail if a key exists in one file but not the other.

```json
// messages/vi.json
{
  "Login": { ... },
  "Feed": {
    "emptyState": "Chưa có kudos nào."
  }
}

// messages/en.json
{
  "Login": { ... },
  "Feed": {
    "emptyState": "No kudos yet."
  }
}
```

---

## Adding a new locale

1. Add the locale code to `LOCALES` in `lib/i18n/config.ts`.
2. Create `messages/{locale}.json` with all existing namespaces and keys.
3. The key-parity test will catch any missing keys on the next test run.

---

## Catalog content

Awards, campaign rules, and badge descriptions are currently single-language (stored as plain text in the database). i18n covers UI strings only. Multi-language catalog content is out of scope for v1.
