## High Priority

### H1 — `t.has()` is not a public API in next-intl v4 (login-error-banner.tsx:27)

**File:** `app/login/_components/login-error-banner.tsx:27`
**Code:**
```ts
const message = t.has(key) ? t(key) : t("error.generic");
```

`t.has()` exists on `TranslationValues` in use-intl (the underlying library), but it is not documented as a stable public API in next-intl v4. The v4 docs do not list `has` on the `t` function object. If next-intl v4 exposes it via the `useTranslations` hook return value it will work at runtime (the build passes), but this usage bypasses type-safety and could silently break on a minor version bump.

**Risk:** Currently green but fragile. If next-intl removes or renames the property, the banner shows `undefined` (React renders nothing for undefined, so the error disappears silently) or throws at runtime.

**Fix — safer pattern:**
```ts
const KNOWN_ERROR_KEYS = ["domain", "oauth", "access_denied"] as const;
type KnownErrorKey = typeof KNOWN_ERROR_KEYS[number];

function isKnown(code: string): code is KnownErrorKey {
  return (KNOWN_ERROR_KEYS as readonly string[]).includes(code);
}

// Inside component:
const message = isKnown(code) ? t(`error.${code}`) : t("error.generic");
```
This removes the dependency on `t.has()`, is fully type-safe, and aligns with how `resolveLocale` guards the cookie value. It also makes it trivial to add new error codes.

### M2 — `NextIntlClientProvider` omits `messages` prop (deviation from plan, relies on v4 implicit behavior)

**File:** `app/layout.tsx:36`
**Code:**
```tsx
<NextIntlClientProvider>{children}</NextIntlClientProvider>
```
**Plan specified:** `getMessages()` + explicit `messages={messages}` prop.

The researcher noted that "without explicit `messages` prop uses `getMessages()` automatically in v4" and the build + runtime probe confirms it works. However:
1. The v4 auto-inheritance is not prominently documented — it works via an internal RSC mechanism that serialises the response from `getRequestConfig` into the client boundary. If this mechanism changes (or if a component is rendered outside the layout's RSC context, e.g. in an isolated test), messages will be undefined and `useTranslations` will throw.
2. The `test/render-with-intl.tsx` helper correctly passes explicit `messages` to avoid this gap in tests, which shows the author is aware of it — but it means production and test paths diverge (prod relies on implicit; tests rely on explicit).
3. The plan deliberately specified explicit `messages` for clarity and safety.

**Fix:** Add `getMessages()` back to the layout and pass it explicitly:
```tsx
import { getLocale, getMessages } from "next-intl/server";
// ...
const locale = await getLocale();
const messages = await getMessages();
// ...
<NextIntlClientProvider messages={messages}>{children}</NextIntlClientProvider>
```
This is one extra call, makes the data flow explicit, and matches both the plan and what `renderWithIntl` already does in tests.

## Low Priority / Nits

### L1 — Cookie missing `secure` flag (locale-actions.ts:15)

```ts
store.set(LOCALE_COOKIE, locale, {
  path: "/",
  maxAge: 60 * 60 * 24 * 365,
  sameSite: "lax",
});
```
`NEXT_LOCALE` is not a secret (it's locale preference), so omitting `httpOnly` is fine. However, omitting `secure` means the cookie travels in plaintext over HTTP. For a production HTTPS app this is a low severity issue (the cookie only stores `vi` or `en`), but it is worth adding `secure: process.env.NODE_ENV === "production"` for completeness.

### L2 — `useLocale() as Locale` cast is safe but fragile (language-switcher.tsx:25)

```ts
const locale = useLocale() as Locale;
```
`useLocale()` returns `string`. The cast is safe only because `resolveLocale` already sanitised the value into `LOCALES` before it reached the cookie. But if in future someone calls `setLocale` bypassing validation (e.g. in a test), this cast silently passes a string that may not be a `Locale`, and `DISPLAY[locale]` returns `undefined`. Not a bug today, but brittle.

**Nit fix:** `const locale = resolveLocale(useLocale()) as Locale;` or add a runtime guard.

### L3 — Image `alt` texts are hardcoded English / untranslated

**Files:** `login-header.tsx:26` (`alt="SAA Logo"`), `login-hero.tsx:34` (`alt="ROOT FURTHER"`)

These are decorative images (logo / wordmark), so empty `alt=""` would arguably be more appropriate (screen readers skip decorative images). If they carry semantic meaning, the alt text should go through translations. Current state: hardcoded English strings in the middle of a Vietnamese UI. Low impact since the images are decorative, but worth noting.

### L4 — `i18n/request.test.ts` is mostly tautological

The test named "i18n/request integration" does not actually test `getRequestConfig` — it tests `resolveLocale` (already covered in `config.test.ts`) and does a trivial `await import()` check. The file's own comment acknowledges this. The "message loading" section's dynamic-import test (`locale = "vi"`) is a template literal with a hardcoded string, not a template literal exercising locale validation — it cannot catch the case where the path is constructed with an unvalidated value. This is acceptable given the architectural constraint (can't easily test RSC internals with Vitest), but the test gives false confidence. Consider removing the duplicate `resolveLocale` assertions or clearly labelling the file as "documentation tests" (which the comment already does).

### L5 — `pnpm-workspace.yaml` `allowBuilds` additions

Added: `@parcel/watcher`, `@swc/core`, `sharp`, `unrs-resolver`. These are build-time native addons allowed by pnpm. No security concern here — all are well-known Next.js/tooling dependencies. Confirm `sharp` is used (Next.js image optimization) and `@parcel/watcher` + `@swc/core` are pulled in by Vitest/SWC — if any of these were not already in the project before this PR, document why.

## Edge Cases Found (Scouting)

**EC1 — Dynamic import path: path-injection risk assessed as negligible.**
`await import(\`../messages/${locale}.json\`)` — `locale` is the output of `resolveLocale()`, which returns one of `["vi", "en"]` (the `as const` tuple). `LOCALES.includes()` is the guard. An attacker who can write arbitrary values to the `NEXT_LOCALE` cookie gets `resolveLocale` to return `"vi"` (the default) — they cannot inject a path like `../../etc/passwd` because the allow-list rejects any non-`LOCALES` value. Safe.

**EC2 — Cookie-to-refresh race condition: correct.**
In `language-switcher.tsx`, `router.refresh()` is called inside `startTransition(async () => { await setLocale(next); router.refresh(); })`. The server action `setLocale` completes (cookie written) before `router.refresh()` fires, because `await` is honoured inside the async transition callback. React 19's `useTransition` supports async callbacks. No race.

**EC3 — Stale-cookie / caching concern: acceptable.**
`cookies()` in `getRequestConfig` forces dynamic rendering. The page is not statically cached. `router.refresh()` invalidates the client-side RSC cache. On Vercel, aggressive CDN caching could in theory return a cached response before the refresh lands — but this is flagged in the researcher report as an unresolved question for staging validation and is not a code defect.

**EC4 — `LoginErrorBanner` dismissed state survives re-render with same code.**
The `useState(false)` for `dismissed` is tied to the component instance. If the parent re-renders with the same `code` prop, the banner stays dismissed (tested and documented). If the URL changes to a different `?error=` code, React remounts the component (different key context) — actually it does NOT remount since neither `key` nor `code` forces a reset. A user who dismisses "domain" and then navigates to `?error=oauth` by other means would see no banner until full page reload. Low probability in practice (error comes from URL query param set by OAuth callback). Acceptable.

**EC5 — `LoginHeader` renders `LanguageSwitcher` inside a `"use client"` boundary.**
`LoginHeader` is marked `"use client"` and `LanguageSwitcher` is also `"use client"`. `LanguageSwitcher` calls `useTranslations("Login")` which requires the `NextIntlClientProvider` context from layout. Since layout wraps all children with the provider, this works. But if `LoginHeader` is ever rendered in isolation (e.g. in a test without `renderWithIntl`), `useTranslations` will throw. Current tests use `renderWithIntl` everywhere — no issue today.

## Positive Observations

- `resolveLocale` is a clean, single-responsibility guard that is tested exhaustively including edge cases (case sensitivity, empty string, null).
- `setLocale` validates before writing — the double-check (`LOCALES.includes(locale)` in both config and action) is intentional defense-in-depth given the TypeScript type already narrows the parameter.
- `messages.test.ts` parity test is real and useful — it recursively compares key trees and will catch missing translations.
- `render-with-intl.tsx` helper using real message files (not mocks) means translation tests assert actual rendered strings, not key names. This is good practice.
- `await searchParams` in `LoginPage` is correct Next.js 16 async dynamic API usage.
- `useTransition` wrapping the `setLocale` + `router.refresh()` sequence correctly marks the UI as pending during the switch, preventing double-clicks.
- Cookie `sameSite: "lax"` is appropriate for a locale preference cookie — no CSRF concern.
- `LoginErrorBanner` renders error messages as plain text via `t()` — no XSS risk from message interpolation.
- Auth behavior unchanged: `GoogleLoginControl` still calls `signInWithGoogle("/")` and error-paths to `/login?error=oauth`.
